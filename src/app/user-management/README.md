# user-management

ผู้ใช้ บทบาทและสิทธิ์ และประวัติการใช้งาน สำหรับแอป React 19 รวมไว้ในโฟลเดอร์เดียว: หน้า ชั้นข้อมูล กฎว่าใครทำอะไรได้ และ UI ที่หน้าเหล่านั้นสร้างขึ้นมา ส่วนอื่นของโปรเจกต์นี้ (navbar, sidebar, หน้า sign-in) คือแอปรอบนอก โฟลเดอร์นี้พอร์ตมาจาก `user-management` ของ `../admin-ng-starter` (Angular 22) หน้าตา พฤติกรรม และสัญญากับเซิร์ฟเวอร์เหมือนกันทุกอย่าง

| โฟลเดอร์ | มีอะไร |
| --- | --- |
| `overview/`, `users/`, `roles/`, `access-reviews/`, `branches/`, `activity/`, `settings/` | หน้าต่างๆ |
| `access/` | `session` (ใครเข้าสู่ระบบและบทบาทอนุญาตอะไร), guard ของ route, หน้า no-access และ dialog ที่เกี่ยวกับการเข้าสู่ระบบ |
| `data/` | type, `AdminApi` (สัญญากับเซิร์ฟเวอร์), `LocalAdminApi` (ข้อมูลตัวอย่างในเบราว์เซอร์), `HttpAdminApi` (เซิร์ฟเวอร์จริง ดู [API.md](API.md)), `adminStore` (state ที่หน้าต่างๆ อ่าน ด้วย Zustand) และกฎสิทธิ์ |
| `shared/` | ชิ้นที่หลายหน้าใช้: badge บทบาทและสถานะ ประโยคกิจกรรม รูปแบบวันที่ ข้อความ error, CSV, เมนู Export (คัดลอก Excel CSV พิมพ์) พร้อมตัวเขียน .xlsx ขนาดเล็กของตัวเอง, ตัวช่วยฟอร์ม (`forms.ts`) และการถามก่อนออกจากหน้า (`leave-guard.ts`) |
| `ui/` | ชิ้นส่วนพื้นฐาน: card ตาราง ฟอร์ม เมนู กราฟ และธีม ดู [ui/README.md](ui/README.md) |
| `i18n/` | ข้อความภาษาไทยและอังกฤษ เป็นไฟล์แปล |
| `index.ts` | สิ่งที่แอป import: route, เมนู, `configureUserManagement()`, `session`, guard, API และ type |

## นำไปใช้ในแอป React อื่น

1. คัดลอกโฟลเดอร์นี้ไปที่ `src/app/user-management` และคัดลอก `build/` ของโปรเจกต์นี้ (plugin ของ Vite ที่ทำให้ style ของ component ทำงานแบบ emulated encapsulation ของ Angular)
2. ติดตั้งสิ่งที่ใช้:

   ```bash
   npm install @floating-ui/dom chart.js i18next lucide-react react-hook-form react-i18next react-router uqr zustand
   npm install -D sass
   ```

3. ใน `vite.config.ts` ใส่ plugin ทั้งสอง และใน `main.tsx` import ธีมก่อน style ของแอปเอง:

   ```ts
   // vite.config.ts
   plugins: [emulatedHosts(), react()],
   css: { postcss: { plugins: [emulatedStyles()] } },
   ```

   ```ts
   // main.tsx
   import './app/user-management/ui/ui.scss';
   import './styles.scss';
   ```

4. ตั้งค่าใน `main.tsx` ก่อน render: แหล่งข้อมูล ภาษา และ session ข้อความผ่าน i18next ซึ่งโหลดไฟล์แปลของแอปและของส่วนจัดการผู้ใช้รวมกัน (ดู `src/app/layout/language.service.ts`):

   ```ts
   import { configureUserManagement, session } from './app/user-management';

   configureUserManagement();          // ข้อมูลตัวอย่าง; เซิร์ฟเวอร์จริงดูหัวข้อ "ใช้เซิร์ฟเวอร์จริง"
   await session.restore();
   const router = createBrowserRouter(routes);
   session.start(navigate, () => router.state.location.pathname);   // ดู src/main.tsx
   ```

   ```ts
   i18next.init({ resources: { th: { translation: { ...appTh, ...userManagementTh } }, en: { … } } });
   ```

5. ใส่หน้าต่างๆ ใน route ระดับบนสุด (หน้าต่างๆ ลิงก์ไปที่ `/users`, `/roles`, `/activity` และ `/settings`) แต่ละหน้าตรวจสิทธิ์ของผู้ใช้ที่เข้าสู่ระบบเองผ่าน loader:

   ```tsx
   import { guard, lazyPage, session, signedOut, USER_MANAGEMENT_ROUTES } from './user-management';

   export const routes: RouteObject[] = [{
     Component: App,
     children: [
       // หน้าแรกที่บทบาทของผู้ใช้อนุญาต หรือหน้า sign-in
       { index: true, loader: () => redirect(session.view.homeUrl()), Component: () => null },
       ...USER_MANAGEMENT_ROUTES,
       { path: 'login', loader: guard(signedOut), lazy: lazyPage(() => import('./login/login'), m => m.LoginComponent) },
     ],
   }];
   ```

6. ให้แอปมีหน้า sign-in (ของโปรเจกต์นี้อยู่ใน `src/app/auth/login`) ซึ่งเรียก `session.signIn()` แล้วเปิด query parameter `returnUrl` ที่ guard ตั้งไว้ หรือ `session.view.homeUrl()`:

   ```ts
   await session.signIn(email, password, remember);
   ```

   guard ส่งคนที่ยังไม่เข้าสู่ระบบไปที่ `/login` ส่ง `signInPath` ให้ `configureUserManagement()` เพื่อใช้ address อื่น

   ลิงก์ในอีเมลพาไปอีกสองหน้า `/activate` และ `/reset-password` และ "ลืมรหัสผ่าน?" ในหน้า sign-in พาไป `/forgot-password` ของโปรเจกต์นี้อยู่ใน `src/app/auth/set-password` และ `src/app/auth/forgot-password` ซึ่งเรียก `AdminApi.acceptInvitation()`, `confirmPasswordReset()` และ `requestPasswordReset()` (API.md หัวข้อ "ลิงก์ในอีเมล") และอ่านความยาวรหัสผ่านขั้นต่ำจาก `getPasswordPolicy()`

   คนที่บทบาทบังคับให้ใช้การยืนยันตัวตน 2 ขั้นตอนแต่ยังปิดอยู่จะถูกกันไว้ที่ `/setup-two-factor` (`TWO_FACTOR_SETUP_PATH`) ซึ่งมากับ `USER_MANAGEMENT_ROUTES` เป็นหน้าของตัวเองแบบหน้า sign-in: แสดงโดยไม่มี navbar และ sidebar (โปรเจกต์นี้ใส่ไว้ใน `AUTH_PAGES` ใน `src/app/app.tsx`)

7. ใส่หน้าในเมนูของแอป `USER_MANAGEMENT_MENU` คือหนึ่งกลุ่ม "User management" มีลิงก์ต่อหน้าและสิทธิ์ที่แต่ละหน้าต้องใช้ แสดงลิงก์เฉพาะเมื่อ `session.view.canSomewhere(link.permission)` และแสดงกลุ่มเฉพาะเมื่อมีลิงก์ให้แสดง ลิงก์ที่มี `tasks: 'accessReviews'` แสดงให้คนที่มีส่วนร่วมในรอบทบทวนสิทธิ์แม้ไม่มีสิทธิ์ (มี `accessReviews` ใน store) พร้อม `accessReviewsWaiting` เป็นตัวเลขข้างๆ sidebar ของโปรเจกต์นี้ (`src/app/layout/sidebar`) แสดงเป็น dropdown

8. ใส่ชิ้นที่ต้องอยู่ในเปลือกแอป (ดู `src/app/app.tsx`): `<SessionNotices />` เหนือเนื้อหาของหน้า, `<ReauthDialog />`, `<UiConfirmHost />` และ `<UiToaster />`

รูปของผู้ใช้ตัวอย่างอยู่ใน `public/assets/images/faces` ของโปรเจกต์นี้ (Vite เสิร์ฟ `public/` ตามที่เป็น ที่ address `/assets/images/faces` เดียวกับฝั่ง Angular) ถ้าไม่มี avatar จะแสดงอักษรย่อแทน

## ใครทำอะไรได้

แต่ละบทบาทให้สิทธิ์เช่น `users.edit` หรือ `roles.manage` (รายการทั้งหมดอยู่ใน `data/catalog.ts`) หน้าและเมนูถาม `session` ก่อนแสดง action และ guard ใน `access/guards.tsx` กันคนออกจากหน้าที่บทบาทไม่อนุญาต:

```tsx
const session = useSession();

{session.can('users.delete') && <UiButton variant="danger">Delete</UiButton>}
```

การตรวจสิทธิ์ (`can`, `canSomewhere`, `canOn`, `canGive`, `branchesWith`) อยู่บน `SessionView`: `useSession()` ใน component หรือ `session.view` นอก component ซึ่งตามบทบาทและเวลาปัจจุบันเสมอ ส่วนการกระทำ (`signIn`, `signOut`, `resume`, `reauthenticate`) อยู่บน `session` เอง ในเอกสารนี้ `session.can(…)` หมายถึงการตรวจบน view

หน้าที่ใครเปิดไม่ได้จะแสดงหน้า no-access ที่ address เดิมที่ขอ ทุกคนเปิดโปรไฟล์ของตัวเอง และเปลี่ยนชื่อ เบอร์โทร และรูปของตัวเองได้

### บทบาทและการมอบบทบาท

โมเดลเป็นไปตาม NIST RBAC พร้อม role assignment แบบ Microsoft Entra:

- **คนหนึ่งถือได้หลายบทบาท** และมีทุกสิทธิ์ของแต่ละบทบาทรวมกัน บทบาทของเขาคือ `RoleAssignment` ใน `User.roles` แต่ละตัวมีวันเริ่ม วันจบ (`null` คือถาวร) และเหตุผล แท็บ "บทบาทและสิทธิ์" ของโปรไฟล์แสดงรายการ ทั้งที่มีผล รอเริ่ม และจบแล้ว และมอบ ต่ออายุ ต่อใหม่ หรือถอดได้ รายชื่อผู้ใช้มอบหรือถอดบทบาทให้ทุกคนที่เลือกได้
- **มอบบทบาทเป็นช่วงเวลาได้** นับตั้งแต่ `startsAt` จนถึง `endsAt` แล้วหยุดเอง `roleAssignmentState()` ใน `data/access-rules.ts` บอกว่าอยู่สถานะไหน `now` ใน store เลื่อนทุกครั้งที่มีการเริ่มและจบ สิทธิ์ badge และตัวเลขจึงตามไปโดยไม่ต้อง reload การมอบที่จบแล้วยังอยู่บนโปรไฟล์ เพื่อต่อใหม่ได้ จนกว่าประวัติการใช้งานจะลืมมัน
- **แต่ละบทบาทมีกฎการมอบของตัวเอง** (`Role.assignment`): ระยะยาวสุด (`maxDays`) ที่ต้องจบหลังจากนั้น และต้องใส่เหตุผลหรือไม่ ตั้งได้ที่หน้าบทบาท
- **บทบาทในตัวระบบ** (Administrator, Manager) ใช้ชื่อ คำอธิบาย และสิทธิ์ตามที่โค้ดของเซิร์ฟเวอร์ให้ สีและกฎเปลี่ยนได้ "ทำสำเนา" คัดลอกเป็นบทบาทของคุณเอง
- **ต้องมีคนดูแลระบบได้เสมอ:** เซิร์ฟเวอร์ไม่ยอมถอด จำกัดเวลา ระงับ หรือลบ คนที่ active คนสุดท้ายที่ถือทุกสิทธิ์แบบถาวร (`last_administrator`)

ไม่มีใครมอบบทบาทที่ให้สิทธิ์ที่ตัวเองไม่มี ดูแลคนที่บทบาท (ตอนนี้หรือที่รอเริ่ม) ให้สิทธิ์ที่ตัวเองไม่มี หรือเปลี่ยนบทบาทของตัวเอง [API.md](API.md#การมอบบทบาท) มี request และกฎที่เซิร์ฟเวอร์ตรวจ

### บทบาทที่ห้ามถือร่วมกัน

เหมือน static separation of duty ของ NIST RBAC กฎหนึ่งข้อระบุบทบาทที่ห้ามใครถือพร้อมกัน คนเดียวจึงไม่ทั้งทำและตรวจงานเดียวกัน หน้าบทบาทและสิทธิ์พาไปที่กฎเหล่านี้ (`/roles/conflicts` พร้อมจำนวนคนที่ต้องแก้) `roles.manage` เพิ่ม แก้ และลบกฎได้ การมอบบทบาทที่ชนกับบทบาทที่คนนั้นถือในช่วงเวลาที่ทับกัน ในขอบเขตใดก็ตาม ถูกปฏิเสธด้วย `role_conflict` dialog มอบบทบาทบอกชื่อกฎก่อน และแถวที่นำเข้าที่มีสองบทบาทแบบนี้แสดงเป็นปัญหา กฎที่สร้างขึ้นระหว่างที่มีคนถือบทบาทของมันอยู่แสดงพวกเขาเป็นคนที่ต้องแก้ เหมือนรอบทบทวนสิทธิ์ (`selectRoleConflictViolations` ใน `data/admin-store.ts`, `roleConflict()` ใน `data/access-rules.ts`)

### สาขา

สาขา (สถานที่ สำนักงาน) มีหรือไม่มีก็ได้: แสดงเมื่อการตั้งค่าเปิด "ใช้สาขา" และข้อมูลตัวอย่างเปิดไว้ เมื่อเปิด:

- **แต่ละคนสังกัดหนึ่งสาขาหรือไม่สังกัดเลย** เหมือนที่ Google Workspace ให้ผู้ใช้แต่ละคนอยู่ใน organizational unit เดียว ฟอร์มผู้ใช้เลือกสาขา รายชื่อผู้ใช้แสดงและกรองตามสาขา (`/users?branch=<id>` หรือ `none`) และไฟล์นำเข้าระบุด้วยรหัสหรือชื่อในคอลัมน์ Branch ได้
- **มอบบทบาทสำหรับสาขาเดียวได้** (`RoleAssignment.branchId`) เหมือนที่ Azure RBAC มอบบทบาทที่ scope หนึ่ง อนุญาตสิ่งที่อนุญาตในสาขานั้นและไม่ที่อื่น: `session.can(permission, branchId)` ตอบว่าได้สำหรับสาขานั้น และ `session.branchesWith(permission)` บอกรายการสาขา `session.can(permission)` ที่ไม่ระบุสาขานับเฉพาะบทบาทสำหรับทั้งองค์กร และเฉพาะบทบาทเหล่านั้นที่นับเป็นผู้ดูแลระบบ (`last_administrator`) ส่วนจัดการผู้ใช้รับสิทธิ์สี่ตัวจากบทบาทของสาขาด้วย (ดู [ผู้ดูแลสาขา](#ผู้ดูแลสาขา))
- **หน้าสาขา** (`branches.view` อยู่ใต้ User management; `branches.manage` เพื่อแก้) เพิ่ม เปลี่ยนชื่อ ปิด และลบสาขา และค้นหา กรองตามสถานะ เรียง และแบ่งหน้ารายการแบบเดียวกับรายชื่อผู้ใช้ สาขาที่ปิดเก็บคนและบทบาทไว้ แต่ไม่มีใครใหม่เข้าสังกัดหรือได้บทบาทที่นั่น สาขาที่มีคนสังกัดหรือถือบทบาทอยู่ลบไม่ได้

โมดูลของแอปเองใช้ขอบเขตสาขากับข้อมูลของตัวเองได้ เช่นสาขาของคำสั่งซื้อ: `session.can('orders.approve', order.branchId)`

### ผู้ดูแลสาขา

เหมือน administrative unit ของ Microsoft Entra และผู้ดูแล organizational unit ของ Google Workspace บทบาทที่จำกัดไว้ที่สาขาให้ `users.view`, `users.create`, `users.edit` และ `activity.view` เหนือคนที่สังกัดสาขานั้น (`BRANCH_SCOPED_PERMISSIONS` ใน `data/access-rules.ts`) ผู้จัดการสาขาจึงดูแลพนักงานของสาขาตัวเองและไม่ใช่ใครอื่น การลบคน บทบาท การตั้งค่า สาขา และการ export ประวัติยังต้องมีบทบาทสำหรับทั้งองค์กร "Branch manager" ในข้อมูลตัวอย่างถือ Viewer สำหรับทุกคน และ Manager เฉพาะเชียงใหม่ สำหรับคนแบบนี้:

- **เมนูและ guard** ถาม `session.canSomewhere(permission)` หน้าผู้ใช้และประวัติการใช้งานจึงเปิดได้ และปุ่มของทั้งหน้าแสดง (เพิ่มผู้ใช้)
- **แต่ละคน** ว่าไปตาม `session.canOn(permission, user)`: สิทธิ์เหนือสาขาของคนนั้น และกฎข้อ 3 ที่นับตามขอบเขต (`permissionsIn`) ทุกสิทธิ์ของแต่ละบทบาทที่เขาถือในขอบเขตของบทบาทนั้น บทบาทสำหรับทั้งองค์กรที่อนุญาตมากกว่าของผู้จัดการเองทำให้ผู้ถือเกินมือ รายชื่อผู้ใช้บอกว่าทำไมแถวนั้นติ๊กไม่ได้
- **คนใหม่** เข้าสังกัดหนึ่งในสาขาของเขา (ฟอร์มเสนอแค่สาขาเหล่านั้น ไม่มี "ไม่มีสาขา") และถ้าไม่มีบทบาทจะได้บทบาทเริ่มต้นจำกัดไว้ที่สาขานั้น การนำเข้าให้บทบาทจำกัดไว้ที่สาขาของแถว
- **บทบาท** มอบได้เฉพาะแบบจำกัดไว้ที่สาขาของเขา (`session.canGive(role, branchId)`): "ใช้ใน" ของ dialog มอบบทบาทแสดงสาขาเหล่านั้น และเสนอบทบาทที่เขาถือที่นั่น
- **ประวัติการใช้งาน** แสดงรายการเกี่ยวกับคนของสาขาเขา เซิร์ฟเวอร์ตอบเฉพาะรายการเหล่านั้น

[API.md](API.md#ผู้ดูแลสาขา) มีกฎที่เซิร์ฟเวอร์ตรวจ `LocalAdminApi` ตรวจเหมือนกัน

### การทบทวนสิทธิ์

เหมือน access review ของ Microsoft Entra และการตรวจเป็นระยะที่ ISO 27001 และเกณฑ์ความเสี่ยงด้าน IT ของธนาคารแห่งประเทศไทยกำหนด รอบทบทวนถามว่าแต่ละคนยังต้องใช้บทบาทที่ถืออยู่หรือไม่ (`/access-reviews` อยู่ใต้ User management; `reviews.manage` เพื่อเริ่มรอบ):

- **เริ่มรอบ** เลือกบทบาท (บทบาทเดียว หรือทุกบทบาท) ของใคร (คนของสาขาหนึ่ง หรือทุกคน) วันปิด และถ้าต้องการ คนที่ตัดสินได้ทั้งหมดนอกจากผู้ดูแลของแต่ละคน เช่นหัวหน้าแผนก ครอบคลุมการมอบบทบาทที่มีอยู่ตอนนั้นหรือภายหลัง เก็บไว้ตามที่เป็น รายงานจึงอ่านได้เหมือนเดิมหลังคนหรือบทบาทเปลี่ยน dialog บอกว่าจะครอบคลุมกี่รายการ
- **การตัดสิน** คนที่ดูแลแต่ละคน (ที่ดูแลเขาได้ด้วย `users.edit` ผู้จัดการสาขาจึงตัดสินให้พนักงานของสาขาตัวเอง) และคนที่รอบระบุชื่อ เลือก Keep หรือ Remove ให้แต่ละบทบาท ทีละรายการหรือทุกคนที่เลือก Remove ถามเหตุผล บังคับในที่ที่การตั้งค่าขอเหตุผลสำหรับการถอดบทบาท ไม่มีใครตัดสินบทบาทของตัวเอง ไม่มีอะไรเปลี่ยนก่อนปิด และเปลี่ยนการตัดสินได้จนถึงตอนนั้น ลิงก์ในเมนูแสดงให้ทุกคนที่มีบทบาทต้องตัดสิน พร้อมจำนวน และหน้าภาพรวมก็บอกด้วย
- **การปิด** สิ้นวันสุดท้ายเซิร์ฟเวอร์ปิดเอง หรือคนที่มี `reviews.manage` ปิดก่อน (การเปลี่ยนแปลงที่เสี่ยง: อาจถามรหัสผ่านอีกครั้ง) บทบาทที่ตัดสิน Remove ถูกถอด ที่ไม่มีใครตัดสินยังอยู่ โดยทำเครื่องหมายว่าไม่ได้ทบทวน ของผู้ดูแลระบบคนสุดท้ายยังอยู่ รอบที่ปิดแล้วไม่เปลี่ยนอีกและลบไม่ได้: Export ให้รายงานที่ผู้ตรวจสอบขอ (Excel, CSV หรือพิมพ์) พร้อมแต่ละการตัดสิน ใครตัดสิน เมื่อไร ทำไม และผลเป็นอย่างไร

[API.md](API.md#การทบทวนสิทธิ์) มี request และกฎ `LocalAdminApi` ทำตามนั้น

## ความปลอดภัย

แท็บความปลอดภัยของโปรไฟล์ (`/users/:id?tab=security`) แสดง:

- **การยืนยันตัวตน 2 ขั้นตอน** เปิดโดยสแกน QR code ด้วยแอป authenticator (Google Authenticator, Microsoft Authenticator, 1Password) แล้วพิมพ์รหัส หลังจากนั้นการเข้าสู่ระบบถามรหัสด้วยนอกจากรหัสผ่าน ผู้ดูแลปิดให้คนที่ทำโทรศัพท์หายได้ QR code วาดด้วย `uqr` ที่โหลดเฉพาะตอนเปิด dialog ตั้งค่า
- **การเข้าสู่ระบบที่ล้มเหลว** การปฏิเสธคนที่มีอยู่จริง (รหัสผ่านหรือรหัสผิด บัญชีถูกระงับ คำเชิญยังไม่ตอบรับ) แสดงในประวัติการใช้งานเป็น "เข้าสู่ระบบไม่สำเร็จ" พร้อมสาเหตุ เช่นเดียวกับรหัสผ่านผิดตอนยืนยันว่าเป็นคุณ เซิร์ฟเวอร์ยังบันทึกเมื่อผิดหลายครั้งจนบัญชีถูกล็อก อีเมลที่ไม่ใช่ของใครไม่ถูกบันทึก
- **รหัสกู้คืน** การเปิด 2 ขั้นตอนแสดงรหัสใช้ครั้งเดียวสิบตัว เช่น `abcde-fghjk` ให้คัดลอกหรือดาวน์โหลด (`RecoveryCodes`) และจะไม่แสดงอีก ทุกที่ที่ถามรหัส (เข้าสู่ระบบ ยืนยันว่าเป็นคุณ ปิด 2 ขั้นตอน) "ทำโทรศัพท์หาย? ใช้รหัสกู้คืน" ใช้รหัสกู้คืนแทน (`TwoFactorCodeField`) แท็บความปลอดภัยบอกว่าเหลือกี่ตัว และสร้างชุดใหม่แทนชุดเดิมได้ (การเปลี่ยนแปลงที่เสี่ยง: อาจถามรหัสผ่านอีกครั้ง) การปิด 2 ขั้นตอนลบทิ้ง [API.md](API.md#รหัสกู้คืน) มี request
- **รหัสผ่าน** การเปลี่ยนทำให้ออกจากระบบบนอุปกรณ์อื่น
- **อุปกรณ์ที่เข้าสู่ระบบ** เบราว์เซอร์ ระบบ IP และกิจกรรมล่าสุดของแต่ละ session ออกจากระบบทีละเครื่อง หรือเครื่องอื่นทั้งหมด

ทุกคนเห็นแท็บความปลอดภัยของตัวเอง คนที่มี `users.edit` เห็นของคนที่ตัวเองดูแลด้วย

## อัปเดตแบบสด

`adminStore` โหลดข้อมูลใหม่ทุกครั้งที่ `AdminApi.watch()` แจ้งว่ามีการเปลี่ยนแปลง กับข้อมูลตัวอย่าง จะเกิดเมื่อแท็บอื่นของเบราว์เซอร์เปลี่ยนอะไรบางอย่าง สองหน้าต่างจึงตรงกัน และ session ที่จบในหน้าต่างหนึ่งถูกสังเกตในอีกหน้าต่าง กับ `HttpAdminApi` ส่ง `events: true` เมื่อเซิร์ฟเวอร์ stream event การเปลี่ยนแปลงแล้ว (ดู [API.md](API.md#อัปเดตแบบสด))

ในมุมมองเข้าถึงง่าย (`useUiAccessibleView`) หน้าไม่เปลี่ยนเอง: `holdChanges` ของ store เปิด การเปลี่ยนแปลงจากที่อื่นจึงตั้ง `changesWaiting` แล้วรอ `adminStore.showChanges()` และ session ที่จบตั้ง `paused` ของ `session` แทนการพาไปหน้า sign-in เพื่อเข้าสู่ระบบใหม่บนหน้าเดิมด้วย `session.resume()` ใส่ `<SessionNotices />` เหนือเนื้อหาของหน้า และ `<ReauthDialog />` ในเปลือกแอป (ดู `src/app/app.tsx`) สองตัวนี้แสดงสิ่งเหล่านี้ให้คนเห็น

กฎบางข้อเกินกว่าสิทธิ์เดี่ยว เพื่อไม่ให้ใครยกสิทธิ์ตัวเองหรือล็อกทุกคนออก: ไม่มีใครมอบบทบาทหรือสิทธิ์ที่ตัวเองไม่มี ดูแลคนหรือแก้บทบาทที่อนุญาตมากกว่าของตัวเอง หรือเปลี่ยนบทบาท สถานะ หรือสิทธิ์ของบทบาทของตัวเอง `data/access-rules.ts` มีกฎเหล่านี้ และ `LocalAdminApi` บังคับใช้เหมือนเซิร์ฟเวอร์ รับเฉพาะฟิลด์ที่แต่ละ request ตั้งได้

### เหตุผล

การเปลี่ยนแปลงที่ถอนหรือรีเซ็ตสิทธิ์ของใครถามว่าทำไม เหมือนที่ Microsoft Entra ถาม justification: ระงับหรือเปิดใช้ใครอีกครั้ง ลบคน ถอดบทบาท รีเซ็ตรหัสผ่านหรือ 2 ขั้นตอนของใคร และพาใครออกจากอุปกรณ์ของเขา ที่ที่หน้าถามก่อนการเปลี่ยนแปลงแบบนี้อยู่แล้ว คำถามนั้นมีช่องเหตุผล การตั้งค่ากำหนดว่าที่ไหนต้องใส่ และการเปลี่ยนแปลงที่ไม่ได้ถามอะไรก่อนจะถามเฉพาะตอนนั้น `reasonPrompt` (`shared/reason-prompt.ts`) ทำสิ่งนี้บน `uiConfirm.prompt` ประวัติการใช้งานเก็บเหตุผลเป็น `Activity.reason` แสดงใต้รายละเอียดและในรายการ ค้นหาและ export ได้ ประวัติของโปรไฟล์ก็แสดงด้วย เหตุผลของการมอบบทบาทใหม่คือเหตุผลของรายการนั้น [API.md](API.md#เหตุผล) มี request

### ยืนยันว่าเป็นคุณ

เหมือน sudo mode ของ GitHub และ reauthentication ของ Microsoft Entra การเปลี่ยนแปลงที่อาจยึดระบบหรือกันคนออกถามรหัสผ่านอีกครั้ง เมื่อคนนั้นเข้าสู่ระบบ หรือยืนยันครั้งล่าสุด นานกว่าที่การตั้งค่าอนุญาต (10 นาทีบนการติดตั้งใหม่): มอบ เปลี่ยน หรือถอดบทบาท (รวมบทบาทของผู้ใช้ใหม่) เปลี่ยนสิ่งที่บทบาทอนุญาตหรือลบบทบาท ลบคน รีเซ็ตรหัสผ่านหรือ 2 ขั้นตอนของคนอื่น พาคนอื่นออกจากระบบ และเปลี่ยนการตั้งค่า เซิร์ฟเวอร์ปฏิเสธการเปลี่ยนแปลงแบบนี้ด้วย `reauth_required` แล้ว `adminStore` รอระหว่างที่ `<ReauthDialog />` ถามรหัสผ่าน (และรหัส ถ้าเปิด 2 ขั้นตอน) แล้วส่ง request เดิมอีกครั้ง หน้าและสิ่งที่พิมพ์ไว้จึงอยู่เหมือนเดิม ปิด dialog แล้วการเปลี่ยนแปลงไม่ถูกส่ง `reauthRequested` ใน store และ `session.reauthenticate()` กับ `session.cancelReauth()` เป็นตัวขับ [API.md](API.md#ยืนยันว่าเป็นคุณ) มีรายการและ request

## การตั้งค่า

หน้าการตั้งค่า (`settings.view` เพื่อเปิด, `settings.manage` เพื่อแก้) กำหนด:

- บทบาทที่ฟอร์มเพิ่มผู้ใช้เลือกไว้ก่อน
- โดเมนอีเมลที่ผู้ใช้ใหม่มีได้
- คำเชิญอยู่ได้นานเท่าไรก่อนหน้าภาพรวมแสดงว่าหมดอายุ
- ปล่อยแอปไว้ไม่ได้ใช้นานเท่าไรก่อน `session` พาออกจากระบบ เซิร์ฟเวอร์ก็จบ session ที่ไม่มี request นานขนาดนั้นด้วย
- บทบาทไหนต้องเปิด 2 ขั้นตอนก่อนทำอย่างอื่น (guard จะกันไว้ที่ `/setup-two-factor`)
- กฎรหัสผ่าน: ความยาวขั้นต่ำ และรหัสล่าสุดกี่ตัวที่ห้ามใช้ซ้ำ
- ประวัติการใช้งานเก็บแต่ละรายการนานเท่าไร: อย่างน้อย 90 วัน ตามที่ พ.ร.บ. ว่าด้วยการกระทำความผิดเกี่ยวกับคอมพิวเตอร์ให้ผู้ให้บริการเก็บข้อมูลจราจร
- คนสังกัดสาขาหรือไม่ (ดู [สาขา](#สาขา))
- การเปลี่ยนแปลงไหนต้องมีเหตุผล (ดู [เหตุผล](#เหตุผล)) บนการติดตั้งใหม่คือการระงับหรือเปิดใช้ใครอีกครั้ง และการลบคน
- การเข้าสู่ระบบหรือการยืนยันรหัสผ่านใช้กับการเปลี่ยนแปลงที่เสี่ยงได้นานเท่าไร (ดู [ยืนยันว่าเป็นคุณ](#ยืนยันว่าเป็นคุณ)) หรือไม่ถามอีกเลย
- บัญชีที่ไม่มีใครเข้าสู่ระบบกี่วันจะถูกระงับทุกคืน (ปิดบนการติดตั้งใหม่; ไม่ระงับผู้ดูแลระบบคนสุดท้าย)
- ภาษาของอีเมลถึงคนที่ยังไม่เคยใช้แอป เช่นคนที่เพิ่งถูกเชิญ (ไทยบนการติดตั้งใหม่)

เซิร์ฟเวอร์ยังส่งอีเมลถึงคนเมื่อบัญชีถูกเข้าสู่ระบบจากอุปกรณ์ใหม่ ได้บทบาท หรืออีเมลหรือรหัสผ่านเปลี่ยน และเมื่อถูกระงับเพราะไม่ได้ใช้ ([API.md](API.md#อีเมลแจ้งเรื่องบัญชีของคุณ)) กับข้อมูลตัวอย่าง อีเมลเหล่านี้ไปที่ console ของเบราว์เซอร์

อีเมลแต่ละฉบับเป็นภาษาไทยหรืออังกฤษ ตามภาษาที่คนนั้นใช้แอปครั้งล่าสุด: `session` บันทึกเป็น `User.language` เมื่อเขาเข้าสู่ระบบ และอีกครั้งทุกครั้งที่สลับภาษา โปรไฟล์แสดงเป็นภาษาของอีเมล และฟอร์มผู้ใช้ตั้งให้คนใหม่ได้ คำเชิญจึงมาในภาษานั้น จนกว่าจะรู้ การตั้งค่าข้างบนเป็นตัวกำหนด ([API.md](API.md#ภาษาของอีเมล)) การเปลี่ยนไม่เขียนอะไรลงประวัติการใช้งาน

`settings` ใน store (`useAdmin().settings`) เก็บค่าเหล่านี้ให้ทุกหน้าที่ต้องใช้

## ลองกับข้อมูลตัวอย่าง

`LocalAdminApi` เก็บผู้ใช้ตัวอย่าง 48 คน บทบาท 14 บทบาท กิจกรรมหนึ่งเดือน และรอบทบทวนสิทธิ์สองรอบ (รอบหนึ่งเปิดอยู่ ของคนเชียงใหม่; อีกรอบปิดแล้ว ของบทบาท Support) ใน `localStorage` ของเบราว์เซอร์ แผนกและชื่อรอบทบทวนอ่านเป็นภาษาของหน้าจอ (รอบทบทวนผ่าน `localName` ใน `shared/formatting.ts`) ชื่อที่ใครพิมพ์เองอ่านตามที่พิมพ์ มีบทบาทในตัวระบบสี่บทบาท และอีกสิบที่องค์กรอาจเพิ่ม (Help desk, HR, Auditor และอื่นๆ) หน้าต่างๆ จึงแสดงรายการบทบาทที่ยาวขึ้น เมื่อมีบทบาทมากกว่าหก หน้าบทบาทค้นหารายการได้ ฟอร์มผู้ใช้เสนอบทบาทเป็น dropdown และกราฟในหน้าภาพรวมรวมทุกบทบาทยกเว้นห้าบทบาทที่ใหญ่ที่สุด หน้า sign-in มีบัญชีให้หนึ่งบัญชีต่อบทบาทในตัวระบบ (Administrator, Manager, Support และ Viewer) อีเมลของผู้ใช้ active คนอื่นก็ใช้ได้ กับรหัสผ่านอะไรก็ได้ 6 ตัวอักษรขึ้นไป ลบ key `admin-data-v8` ในเบราว์เซอร์เพื่อเริ่มใหม่

## ใช้เซิร์ฟเวอร์จริง

ทำ endpoint ใน [API.md](API.md) หรือรัน `admin-api-starter` ซึ่งเป็นเซิร์ฟเวอร์ Spring Boot ข้างโปรเจกต์นี้ที่ทำไว้ครบ แล้วเปลี่ยนเป็น `HttpAdminApi`:

```ts
configureUserManagement({ api: new HttpAdminApi({ url: '/api', events: true }) });
```

ให้ API อยู่ origin เดียวกับแอป: `npm run dev` ของโปรเจกต์นี้ส่งต่อ `/api` ไปที่เซิร์ฟเวอร์ที่ `http://localhost:8080` ด้วย `server.proxy` ใน `vite.config.ts` `HttpAdminApi` เก็บ access token อายุสั้นไว้ในหน่วยความจำเท่านั้นและส่งเป็น bearer token ส่วน refresh cookie แบบ HttpOnly ขอ token ใหม่หลัง reload หรือเมื่อหมดอายุ (ดู [API.md](API.md#การเข้าสู่ระบบ-access-token-และ-refresh-cookie))

หน้าต่างๆ คุยกับ `adminStore` และ `session` เท่านั้น จึงไม่มีอะไรอื่นต้องเปลี่ยน สำหรับ backend แบบอื่น (GraphQL, Firebase, Supabase) เขียนคลาสที่ extends `AdminApi` แล้วส่งเป็น `api` ไม่ว่าแบบไหน เซิร์ฟเวอร์ต้องตรวจสิทธิ์เอง: การซ่อนปุ่มไม่เคยหยุด request

ถ้าจะเข้าสู่ระบบผ่าน identity provider (OIDC, Azure AD, Google) แทนฟอร์มรหัสผ่าน ให้ library ของ provider จัดการ redirect แล้วให้ `getSession()` คืนผู้ใช้ที่เซิร์ฟเวอร์จับคู่กับบัญชีของ provider
